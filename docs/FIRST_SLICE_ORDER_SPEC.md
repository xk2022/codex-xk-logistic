# 首片訂單欄位與驗收規格提案

日期：2026-11-17（Asia/Taipei）。主要任務：[Issue #4](https://github.com/xk2022/codex-xk-logistic/issues/4)。
狀態：Proposed（D04 及關聯子項待使用者確認）。本輪交付規格、欄位表及合成案例，尚未建立產品程式、正式 DB／OpenAPI 或執行產品測試。

## 已確認與本輪建議

已確認：單公司三角色、一單多貨櫃／貨物項目、每項目可多段、依前置條件執行、每任務同時最多一組有效派工；手機照片回報及出發前撤改／出發後異常／作業完成且可離場才釋放的原則。已採用的技術仍依 [決策紀錄](06-decisions-and-acceptance.md) 與 ADR-0002～0006。

本輪只將既有 [L1 欄位矩陣與案例](L1_BUSINESS_MODEL.md)、[資料與流程](04-domain-and-workflows.md) 及 [L2 範圍／驗收](L2_MVP_AND_ACCEPTANCE.md) 收斂成首片可審閱規格。來源基準為 Logistics 提交 9fde649613b6b7712624be2810aabc96b6e75c6b。具體必填時點、例外、聯絡人規則及正式代碼仍未獲業務核准；表格與案例不當作已確認現場事實。

## 首片邊界與後續階段

首片實作目標仍為「主檔與多項目／多段訂單可保存、可重讀」。本頁列受理／派工／出發／回報時點，是為確認資料完整性，不會因此把派工、手機、照片與結案全部擴張成首片必交功能，也不把它們移出完整 MVP。

| 階段 | 本輪建議的資料檢核 | 本輪／首片界線 |
|---|---|---|
| 草稿保存與修改 | 類型、有效客戶；已提供值合法；所提供關聯同單、無環；伺服器欄位不可冒用 | 本輪規格；採用且符合開工前提後才實作保存／查詢。 |
| 受理 | P02／P03 的項目、路線及類型資訊完整 | 本輪提出受理檢核，受理動作端點與狀態代碼依正式契約排定，不因欄位表存在視為已實作。 |
| 派工 | 計畫起訖時間、適用重量及其他核定限制 | 沿 L1 後續切片；重量來源／未知重量、空櫃及超載核對例外仍待確認。 |
| 出發 | 前置段的實際交接就緒、進口提重所需放行／櫃號等條件 | 沿 L1，放行與出口通關／截止政策待核定，不將「先前任務存在」當成「已就緒」。 |
| 回報／釋放／結案 | 該段證據、出口提空補櫃號、可離場確認及行政／整單守衛 | 沿 L1／L2 及既有已確認原則；照片／確認人／異常子項仍待確認。本輪沒有建立執行事件欄位或守衛程式。 |

受理所需的集合完整性由 P02 定義；單純某欄位不為空不代表整單可受理。未知重量、櫃號與日期使用明確的未知／null 語意，禁止把未知自動填 0、今日或假櫃號。若已提供起訖時間，保存時也應檢查時間先後；缺少派工前資料則保留為未完整草稿，不靜默建立占用。

AF02 是四個稽核欄位的一筆群組定義；CSV 的 40 筆不等於已建立 40 個資料庫欄位。一般欄位的長度、數值精度、序列化、字典與錯誤碼需正式契約鎖定後再實作。

## 三組合成案例與最小草稿

[案例 JSON](FIRST_SLICE_ORDER_EXAMPLES.json) 是「保存後讀回概念片段」，不是建立 API 請求、DB seed、正式訂單或已執行結果；系統 UUID／單號只是合成示例，未含完整稽核欄位。毛重以十進位字串保留示意精度，正式 JSON 數值表示仍待契約選定。taskKind 的中文標籤是示意，不是已核准 enum。

| 案例 | 內容 | 評審目的與限制 |
|---|---|---|
| 最小草稿 | 進口類型＋有效示意客戶，尚無船務／項目／任務 | 檢查 P01 的最小保存提案，不可受理或派工。 |
| DEMO-IMPORT | 兩櫃、各提重及還空，共四段；每櫃後段依賴其首段 | 檢查不同項目、不同櫃型及前置關係可讀回；櫃號／聯絡人／最後提櫃日尚未知，不能宣稱可出發或符合所有受理例外。 |
| DEMO-EXPORT | 一櫃、提空與交重兩段，先不知道櫃號 | 檢查可在提空後補號的提案；通關／交櫃截止與限制仍未知，補號規則尚未執行驗證。 |
| DEMO-LOCAL | 一個一般貨物項目、兩段中轉，無船務／櫃號 | 檢查類型差異與中轉依賴；不假定中轉等同最終收貨。 |

客戶、地址、識別、船務與日期全部是示意。日期用於跨日／時區評審，沒有建立行事曆排程。資料檔 metadata 明示 synthetic／PROPOSED／runtime_validation=not_run；本輪只檢查檔案內參照與格式。
