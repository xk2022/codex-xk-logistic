## 首片邊界與後續階段

首片實作目標仍為「主檔與多項目／多段訂單可保存、可重讀」。本頁列受理／派工／出發／回報時點，是為確認資料完整性，不會因此把派工、手機、照片與結案全部擴張成首片必交功能，也不把它們移出完整 MVP。

| 階段 | 資料檢核與決策狀態 | 本輪／首片界線 |
|---|---|---|
| 草稿保存與修改 | 類型、有效客戶；已提供值合法；所提供關聯同單、無環；伺服器欄位不可冒用 | P01 已採用；契約已建立，符合開工前提後才實作保存／查詢。 |
| 受理 | P02／P03 的項目、路線及類型資訊完整 | P02／P03 已採用；契約提供只讀 acceptance-check，實際受理動作不在本片，尚未實作。 |
| 派工 | 計畫起訖時間、適用重量及其他核定限制 | 沿 L1 後續切片；重量來源／未知重量、空櫃及超載核對例外仍待確認。 |
| 出發 | 前置段的實際交接就緒、進口提重所需放行／櫃號等條件 | 沿 L1，放行與出口通關／截止政策待核定，不將「先前任務存在」當成「已就緒」。 |
| 回報／釋放／結案 | 該段證據、出口提空補櫃號、可離場確認及行政／整單守衛 | 沿 L1／L2 及既有已確認原則；照片／確認人／異常子項仍待確認。本輪沒有建立執行事件欄位或守衛程式。 |

AF02 是四個稽核欄位的一筆群組定義；CSV 的40筆不等於40個DB欄位。本片長度、序列化與錯誤碼見API契約；字典、業務數值上限及例外仍待確認。

## 三組合成案例與最小草稿

[案例 JSON](FIRST_SLICE_ORDER_EXAMPLES.json) 是「保存後讀回概念片段」，不是建立 API 請求、DB seed、正式訂單或已執行結果；系統 UUID／單號只是合成示例，未含完整稽核欄位。毛重以十進位字串示意；本片契約亦選十進位字串傳輸，計算／保存用BigDecimal／numeric，不保證尾零顯示位數。taskKind 的中文標籤是示意，不是已核准 enum。

| 案例 | 內容 | 評審目的與限制 |
|---|---|---|
| 最小草稿 | 進口類型＋有效示意客戶，尚無船務／項目／任務 | 檢查已採用 P01 的最小保存規格，不可受理或派工。 |
| DEMO-IMPORT | 兩櫃、各提重及還空，共四段；每櫃後段依賴其首段 | 檢查不同項目、不同櫃型及前置關係可讀回；櫃號／聯絡人／最後提櫃日尚未知，不能宣稱可出發或符合所有受理例外。 |
| DEMO-EXPORT | 一櫃、提空與交重兩段，先不知道櫃號 | 保留提空後補號的後續提案（不由P01～P03核准補號時點）；通關／交櫃截止與限制仍未知，補號規則尚未執行驗證。 |
| DEMO-LOCAL | 一個一般貨物項目、兩段中轉，無船務／櫃號 | 檢查類型差異與中轉依賴；不假定中轉等同最終收貨。 |

客戶、地址、識別、船務與日期全部是示意。日期用於跨日／時區評審，沒有建立行事曆排程。舊概念資料檔明示synthetic／ILLUSTRATIVE／runtime_validation=not_run，並記P01～P03已採用；不是本片完整API形狀。另有 [契約正反例](api/ORDER_DRAFT_CONTRACT_EXAMPLES.json)，僅供schema與圖結構靜態驗證。
